# Changelog

## 3.4.0 (unreleased)

### Changed

- The gift card list of the configuration page is rendered by the server with the `BoDataTable` and `BoPagination` components of the default-twig back-office, laid out like its order list: a search (code, order reference, name of the buyer or of the beneficiary), chips for the type (bought, generated by an administrator) and the status, sortable headers (code, amounts, expiration, status), newest cards first, and pages of 25 cards. The order is shown under the code and what was spent under the amount; the buyer and the beneficiary are shown as the order list shows a customer, the flag of the country of their default address before their name and their email under it; a PDF column has one button per active language, marked by its flag; every action is in the row (edit, send by email, and a switch that activates or deactivates the card), and the table fits a laptop screen. The send and switch buttons take the `send`, `activate` and `deactivate` kinds of the default-twig row actions; with a default-twig that does not have them yet, they show the generic glyph and still work. The search, the filters, the sort and the page are query parameters of the module page, so a list can be bookmarked and shared.
- The search and the type filter now apply on the server. They never did: the old table sent them to a route that ignored them, and, as that route only cut pages from the second one, every card was loaded at once.
- Activate and deactivate are plain POST forms. Sent without a script (`X-Requested-With`), they redirect to the page of the list they were sent from, with its filters, sort and page; the answer to a script request stays 204.
- The list script is plain JavaScript (the edit window fill, the usage history, the code given to the send window). jQuery, DataTables, select2, lodash and flatpickr, and every CDN they were loaded from, are gone.
- `GiftCardListInfoProvider::build()` takes the cards of the page and reads the names and order references of those cards only.
- New translation keys in `theliagiftcard.bo.default-twig` (fr_FR, en_US, de_DE); the keys that only served DataTables, and `GENERATE_PDF_GIFT_CARD`, are removed.

- The edit window shows what was already spent of the card and what is left, under its amount, and the message the buyer wrote, as text. `/admin/module/theliagiftcard/show/{code}` returns them (`spent`, `remaining`, formatted in the interface language, and `beneficiary_message`).

- Activate and deactivate read the code of the card from the body of the form, out of the address (logs, history); the query string is still read for a template that has not followed. A form without the token of the session is answered 403 instead of a server error. The list script only posts to the two actions the page names.
- `/admin/module/theliagiftcard/show/{code}` answers 404 for an unknown card.
- Every link of the list (order, customer, PDF, activation) goes through the router.
- The recipient e-mail of the creation and edit windows (`beneficiary_address`) is validated as an e-mail; a refused field goes back to the window with its message instead of an error page. The back office writes the recipient e-mail in `beneficiary_address`; `beneficiary_email` stays the e-mail given by the buyer in the shop.

- The right to change the module is read once per page for the actions of every row, not once per button: the profile of a restricted administrator was read again for each of the 75 buttons of a page.
- The search also reads the e-mail of the buyer and of the beneficiary, as the rows show it.
- The expiration date is written in the date format of the language of the interface (Configuration > Languages).
- The edit window says when the card cannot be read (an expired session, for instance) and cannot be saved empty.

### Fixed

- The creation window of the back office saves the recipient e-mail. It was asked for and dropped, so a card created by an administrator never had one.
- The creation window asks for the recipient e-mail once, under a translated label: the field showed the `FORM_ADD_BENEFICIARY_ADDRESS` key, and the e-mail of the automatic sending, which only serves a card bought in the shop, came after it under the label of the message.
- Missing labels translated: amount, expiration date, list of cards and e-mail subject and text in German, e-mail subject and text in English; the German code field of the shop read "Enter your code here"; « Nom du bénéficaire » misspelt in French.

### Removed

- The `/admin/module/theliagiftcard/show` route and the DataTables helpers of `GiftCardAdminController`, and `HookConfigurationManager::getdefineColumnsDefinition()`. `/admin/module/theliagiftcard/show/{code}` stays: the edit window reads the card from it.

### Template overrides

A shop that overrides `gift-card-config.html.twig` or `datatable.js.html.twig` must follow: the script template is now `gift-card-config-js.html.twig`, and the list is built from `rows`, `filters`, `current_page`, `pages` and `total` (`columnsDefinitionTransaction` and `all_info` are gone). The `#gift-card-status-error` block and the `js-gift-card-status-form` class are gone with the jQuery script. `HookConfigurationManager` takes the list service and presenters in its constructor, and its `defineColumnsDefinition()` is gone: a shop that extends the hook must follow.

## 3.3.0 (unreleased)

Requires Thelia 3.3.0 (`module.xml`, and `conflict` on `thelia/core` below 3.3.0 in `composer.json`).

### Added

- The gift cards are an instant payment means of the core (`InstantPaymentModuleInterface`): the cards put on the cart become one part of the order, settled by the core when the order is paid and released when it is cancelled.
- Front entry on the payment step of the Flexy theme, following the payment parts contract: a live component in the `checkout.payment.parts` theme hook to tick a card, type its code or take the cards off.
- The paid / left-to-pay lines of the checkout summary (3.2.8) stay, and agree with the part the core composes for the order. The `POST /gift-card/spend` form of the summary stays on the steps before the payment.
- `GiftCardOrderList` loop: `status` argument, default 0 (rows spent). Pass 1 for the rows given back.

### Changed

- The checkout summary no longer draws the gift-card form on the payment step (nor on a one-page checkout): the `TheliaGiftCard:PaymentPart` component is the one entry there. The lines stay.
- A row of `gift_card_order` is never deleted: giving it back sets its `status` to 1.
- Giving back is refused (`GiftCardReleaseRefusedException`) when the rows read under the locks do not add up to the part.
- `TheliaGiftCard::pay()` no longer sets the order status: the core turns an order paid in full by cards paid.

### Breaking

- `OrderAfterPayListener::__construct(RequestStack)` is now `__construct(RequestStack, GiftCardPaymentService)`.
- `OrderPayListener::__construct(GiftCardService, GiftCardGenerateService, EventDispatcherInterface, GiftCardPaymentService)` is now `__construct(GiftCardService, GiftCardGenerateService, EventDispatcherInterface)`. `onOrderPayGiftCard(OrderEvent)` and its `ORDER_BEFORE_PAYMENT` subscription are removed: the cards are no longer debited before the payment.
- `PaymentListener::handleGiftCard(OrderPayTotalEvent)` is now `deductWhatWasDebitedBeforePaymentParts(OrderPayTotalEvent)`, on `ORDER_PAY_GET_TOTAL` at priority 60 (`PaymentListener::TOTAL_PRIORITY`). It deducts only for an order with no payment part that has rows in `gift_card_order`, and no longer reads the cards of the cart. Transition, to remove in a later version.
- `GiftCardPaymentService::debitCart(Order $order, int $cartId): void` is replaced by `spend(Order $order, string $amount): void` and `release(int $orderId, ?string $expectedAmount = null, ?ConnectionInterface $connection = null): void`.
